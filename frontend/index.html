    02 / Repository guide

    How CI/CD works

    Workflows say when and what to run. CI configuration tells them which paths, versions, and release branches to use.

    .github/workflows/

    What runs, and when

    01 · Pull requestpr-quality-gate.yml
    Detects what changed, then runs the relevant lint, type checks, tests, builds, and security checks. Docker images are built and smoke-tested, not pushed. The final required job blocks merges only when GitHub’s ruleset requires it.
    02 · Releaserelease.yml
    Runs on pushes to main, version tags, or manual dispatch. It validates the commit and builds multi-architecture images. Only eligible commits with registry credentials can publish. Images are traceable by commit SHA; nothing is deployed automatically.
    03 · Nightly or manualscheduled-checks.yml
    Rechecks dependencies against current advisories, scans Git history for secrets, and reports outdated dependencies without delaying PRs.

    .github/ci/

    Configuration the workflows use

    paths-filter.yaml
    Maps changed files to frontend, backend, shared, Docker, and docs filters so unrelated jobs can skip.
    release-branches.txt
    Lists branches a commit must be reachable from to be eligible for release. DEFAULT means the repository’s default branch.
    toolchain.lock.env
    Records Node and Go versions and Docker base image pins. CI checks that they agree with .tool-versions and the Dockerfiles.
    tools.lock.env
    Pins the analyzers used by CI: govulncheck, Gitleaks, and actionlint.

    Also worth knowing: .ci/security-policies.env holds the scanner thresholds, while scripts/ci/ contains pipeline self-checks. Neither folder contains GitHub Actions workflows.
